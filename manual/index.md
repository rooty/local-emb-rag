# Индекс: обновление, пересборка, порог

Индекс — файл SQLite `db_path` (по умолчанию `./localrag.db`). В нём для каждой статьи
лежат векторы фрагментов текста, вопросов из `questions` и строки `keywords`.
Источник правды — папка `docs_dir`: индекс всегда можно собрать из неё заново.

## Обычное обновление

```bash
./localrag -config config.yaml index
```

Команда сравнивает файлы с индексом по SHA-256: новые и изменённые эмбеддятся заново,
удалённые убираются, остальные не трогаются (`N unchanged`).

`serve` держит индекс в памяти. После `index` ему нужно сказать перечитать индекс:

```bash
kill -HUP <pid serve>        # в логе: reloaded index: N chunks
```

Запускать `index`, пока работает `serve`, можно: SQLite в режиме WAL, а `serve` читает
базу только при старте и по SIGHUP.

## Что пересобирает индекс целиком

`index` сам пересобирает всё (в логе `embedding settings changed, rebuilding the whole index`),
если в config.yaml изменилось:

- `embedding.model`
- `embedding.dims`
- `embedding.doc_prefix` или `embedding.query_prefix`
- `chunk_chars`

а также после обновления localrag со сменой формата индекса.

Не пересобирают: `embedding.base_url`, `api_key`, `batch_size`, `timeout_sec`, все
настройки `search`, `answer`, `language`, `fallback_message`. Если вы перенесли ту же
модель на другой сервер (например, с локальной Ollama на ollama.com), убедитесь, что это
действительно та же модель: иначе векторы будут несовместимы, а индекс об этом не узнает.
В таком случае удалите `localrag.db` и выполните `index`.

Принудительная пересборка:

```bash
rm localrag.db localrag.db-wal localrag.db-shm 2>/dev/null
./localrag -config config.yaml index
```

## Смена модели эмбеддингов

1. Загрузите модель: `ollama pull <модель>`.
2. В config.yaml поменяйте `embedding.model`, при необходимости `dims` и префиксы
   (для BGE-M3 префиксы пустые, пример в `config.example.yaml`).
3. `./localrag -config config.yaml index` — пересоберёт всё.
4. `./localrag -config config.yaml calibrate examples/questions.jsonl` — у новой модели
   своя шкала сходства, старый `min_score` не подходит.
5. Поставьте новый `search.min_score`.
6. Перезапустите `serve` (не SIGHUP!): модель для эмбеддинга вопроса берётся из конфига
   при старте процесса.

Чтобы не останавливать сервис на время пересборки, соберите новый индекс в отдельный файл
(`db_path: ./localrag-new.db` во временном конфиге), затем подмените конфиг и перезапустите `serve`.

## Порог `min_score` и `max_gap`

- `search.min_score` — если лучшая статья похожа на вопрос меньше, сразу отдаётся заготовка
  (`below_threshold`). Подбирается командой `calibrate`.
- Выше порога работает вторая проверка: LLM отвечает `NO_ANSWER`, если в найденных
  статьях ответа нет (`llm_no_answer`). Поэтому порог можно держать чуть ниже, чем
  предлагает `calibrate`, если хотите отвечать на большее число вопросов.
- `search.max_gap` — статьи, которые хуже лучшей больше чем на `max_gap`, не идут ни в
  ответ, ни в источники. Если в источниках видны лишние статьи, уменьшите (например, 0.03).

Как читать вывод `calibrate`:

- `ок` / `мимо` — нашлась ли на первом месте нужная статья. «Мимо» лечится вопросами
  в `questions` нужной статьи, а не порогом;
- строки «в базе: нет» с высоким score — опасные вопросы. Проверьте их через `ask`:
  они должны получить заготовку (`llm_no_answer`);
- «Предлагаемый min_score» — порог, при котором больше всего вопросов на правильной стороне.

Значения на 16 статьях helpdesk с `embeddinggemma` (Ollama, 768): правильные вопросы
0.79–0.97, чужие до 0.865; выбран `min_score: 0.81`. На другой модели или базе цифры
будут другими.

## Резервная копия

Индекс восстанавливается из `docs_dir`, поэтому главное — хранить статьи (лучше в git).
Копию индекса можно снять, когда не идёт `index`: `cp localrag.db backup/`.
